## ADMIN PANEL

**20. Dashboard not loading real data properly.** Everything is backed by real Prisma queries — no hardcoded placeholders found. **21. "Euthanasia Pull" checkbox on intake form.** The backend field (`Kitten.intakeSource`) already exists and the dashboard stat already filters on it — but it's completely unreachable from the UI: missing from `createKittenSchema` entirely, never written by `createKitten`, and no field/checkbox exists anywhere in `KittenForm.jsx` or the edit panel. No schema change needed, but touches validation + controller + new UI, plus a decision on the exact string format written (needs to keep matching the dashboard's `contains: 'Euthanasia'` filter). **Moderate.**

**22. Calendar events don't show on Dashboard.** Two distinct findings: (a) there is no calendar/events widget in `DashboardPage.jsx` at all — never built; (b) separately, a real bug — the backend already computes a ready-to-use "next upcoming public event" summary line (`dashboardInsights.js`), but it's part of the same discarded `alerts` array from #20 and never reaches the client. Rewiring the dropped alert is a **quick fix**; an actual events list/widget is **moderate**.

**23. Outcome-specific fields per status + new "Released" status.** Reconciled against `kitten-outcome-record-plan.md` from last session — that plan is now **insufficient**, not just re-confirmable: it proposed one shared `outcomeDate`/`outcomeType` pair, but this request needs different field *types* per status (Adopted/Deceased/Released → date, Transferred → text), which the plan never anticipated. "Released" also doesn't exist in the current 6-value status enum and isn't mentioned in the old plan at all — based on the literal wording given, this reads as a 7th additive status, not a replacement, but worth a one-line confirmation with the client since it could colloquially overlap with "Transferred." Recommend updating the existing plan doc rather than writing a new one. **Needs its own planning session** (schema change + new enum value + conditional-by-status UI).

**24. "Documents uploaded are showing in pictures."** Root cause found and it's real: there's only one `Document` table for both documents and photos — the split between them is a heuristic (`isPhotoDocument()`) partly based on whether the free-text `docType` field *contains the substring* "Photo". The generic Documents-tab upload form has a free-text Document Type input (not a dropdown) — if staff type anything containing "Photo" (e.g. "Photo release form") on a non-image file, it gets pulled into the photo gallery and renders as a broken image icon. **Moderate** — fix via constraining `docType` to a fixed set and/or hardening the heuristic to require an actual image file type, not just a text match.

**25. Sort options (name/age/gender) on Kittens list.** No sort control exists in the UI at all, and the backend list query has a hardcoded `orderBy` with no query param support. "Gender" would map to the existing `sex` field (no separate gender column); "age" would sort by `dateOfBirth` inverted. Needs a new query param + orderBy branching server-side, plus a new sort control client-side. No schema change. **Moderate.**

**26. No edit/delete for Foster records.** Confirmed fully missing on both sides — no `PUT`/`DELETE` route, no controller functions, no UI buttons anywhere. `kittenController.js` already has a complete update/delete pattern (including FK-constraint error handling) that can be used as a template. Delete needs a real decision: `Placement.fosterId` is `onDelete: Restrict`, so deleting a foster with placement history will fail — likely needs a deactivate-style pattern instead of hard delete. **Moderate.**

**27. Foster capacity doesn't decrease on kitten status change.** Root cause confirmed: displayed capacity is correctly computed live from open `Placement` rows (`dischargeDate: null`) — but changing a kitten's `status` directly (e.g. to Adopted) never touches `Placement`/`currentFosterId` at all. Only the explicit "Discharge Placement" action on the Foster page does that. So status changes and placement discharge are two disconnected systems that are supposed to move together but don't. Fix needs `updateKitten` to auto-discharge the matching placement on certain status transitions — ties directly into #23's new "Released" status and needs the same status-list decision. **Moderate.**

**28. Foster capacity from Application not carried over.** Important finding: `foster-auto-provision-plan.md` is **stale** — it says "Not built" but the feature was actually completed in two later commits (auto-provision endpoint + confirmation modal both exist and match the plan's spec closely, including the maxKittens-stays-at-0 behavior the plan explicitly called out). This QA item is really a *different*, narrower ask than the plan covered: the Application form itself never collects a numeric "how many kittens can you take" value (only a multi-select capability checklist) — so there's nothing to carry over. Recommend confirming with the client whether they actually want a new numeric application field, since staff can already type a capacity into the confirmation modal at approval time. **Needs its own planning session** if a new application field is genuinely wanted (product/UX decision on input type). Also: flag `foster-auto-provision-plan.md` for archiving/updating since its checklist is done.

**38. Protocol day-offset confusion (explain only, no fix proposed).** Mechanism traced precisely: `startDayOffset`/`endDayOffset` are zero-based relative to the activation date's calendar day (0 = same day as activation, inclusive on both ends), truncated to UTC midnight with no time-of-day concept — multiple doses per day share an identical timestamp, differentiated only by a dose-number field, with no indication of when during the day each should actually be given. None of this is explained anywhere in the current UI (bare number inputs labeled "Start/End Day Offset"), which is almost certainly the actual source of confusion. Documented for a future UX pass — no fix proposed per your instructions.

**39. Needs a new field and a change to the core dose-generation loop, plus a UX decision on how it composes with the existing offset/frequency fields. **Needs its own planning session.**

**40. Protocol not linked to health records.** Confirmed: marking a protocol dose "given" only updates the dose row itself — it never creates a corresponding Medication or Vaccine record, and there's no relation between the two systems at all. They're fully separate UI sections and fully separate data. Needs a real design decision (does every dose administration create a permanent health record? Only some? How to distinguish vaccines from general meds when a protocol drug doesn't specify that today) before any code changes. **Needs its own planning session.**
